# External audit — findings, repairs, and cleanup backlog

Audit run 2026-08-19 against the whole repo. This file records what was fixed,
what was deliberately skipped, and what is still outstanding, so none of it
survives only in a chat transcript.

**Framing that reorders the audit's own ranking:** it assessed the entire repo —
hosted SaaS, posting pipeline, Cloud Drop, candidate review, Docker. The live
deployment is one Mac, one phone, X-only curated engagement. Verified at the
time of the audit: `serve-api` and the web server were **not running**, all 28
accounts had `engagement.mode: "off"`, `contents: 0`, `queue: 0`,
`engagementTargets: 0`. Roughly half the "high" findings are real code faults
with **zero exposure** in this deployment.

### Details worth keeping

**Zero-metric rejection was self-inflicted.** `x-posts.ts` required a non-zero
metric to treat a row as a post. X omits zero counts rather than rendering "0",
so a post published minutes ago has a timestamp and nothing else. Added
2026-08-01 to keep chrome rows out — but the timestamp check already did that.
Almost certainly why `@nateherk` returned `no_eligible_post` nine times on
2026-08-14, which the daemon retried as nine full device passes.

**`serve-api` was worse than the audit said.** It flagged CORS `*`. The older
`RED_TEAM_REPORT.md` found the real hazard: it is a *mutating* command, so it
was forwarded to the controller socket and run inside `SerialCommandAuthority`,
where `server.listen()` never closes. Running it once would have **permanently
killed the daemon's command queue** — no warmups, no engagement, no recovery —
with the process alive so launchd never restarted it.

**A wrong code comment kept a bug alive.** The curated-engagement lock guard read
the raw lock table instead of the API, justified by a comment claiming a freshly
loaded store has empty in-memory locks. `load()` calls `locks.restore()`
(`store.ts:256`), so the API was safe all along. The comment was written during
an earlier session on a misreading and then justified the weaker code.

**Where the audit is wrong:** it lists `createProductionTransport` as dead. It
has 4 references and `makeDriver()` uses it. It also rates the curated post-key
mismatch "high"; `engagementTargets` has 0 rows, so `alreadyEngagedKeys` is
always empty and the comparison never fires — latent, not active.

## Cleanup backlog

**Sections 1–8 completed 2026-08-19 in `19768cf`** — operator-facing strings,
the runbook's inverted maintenance wording, the DEVELOPMENT_TEAM stamp, and all
six dead-code items. Verified on hardware: `runner install` succeeded, the team

Remaining work is items 9 onward.

### Original list (1–8 now done)

### Operator-facing wrongness (do first — has already misled the operator)

1. **`cli.ts:765` and `cli.ts:2357` tell the operator to "Open Heiss Runner".**
   The visible app is a stub whose `ControlServer` refuses every action; the real
   automation is `so.heiss.runner.uitests.xctrunner`. This instruction was passed
   on verbatim on 2026-08-13 and sent the operator to a Settings screen with
   nothing to do.
2. **Maintenance mode has inverted English.** `"running"` = farm live,
   `"active"` = paused. `docs/se-restore.md:18` says pause when status shows
   `"active"` — backwards. Directly implicated in the all-day stall of
   2026-08-07.

### Dead code (verified by reference count, not assumed)

3. `requireHumanEngagement` — defaulted `true`, persisted, read by **nothing**
   (`types.ts:341`, `store.ts:82,137`). Reads as a master safety switch; is a
   no-op. Either gate script building on it or delete it.
4. `ProductionIosDriver`, `defaultWarmupActions`, `isClaimable` — one reference
   each, the definition itself. `defaultWarmupActions` ignores its `searchTerms`
   parameter and returns the same array either way.
5. `coordinateForAction` — hardcoded portrait taps (340,520), unreachable since
   `RealUsbTransport` always implements `runScriptAction`. Same class of thing
   that opened X's Grok panel before it was removed from the Swift side.
6. `generateMinimalXcodeproj` — a second embedded copy of the Swift app, used
   only if both the xcodeproj and project.yml are missing. Produces a runner
   with a gesture stub and **no UITests**: silently cannot automate. Fail
   instead.
7. `DeviceDriver.kind` still includes `"simulator"` in a production-only type.

### Known annoyance with a known fix

8. **The Xcode signing team does not stay selected.** `runner install`
   regenerates `~/.heiss/runner-build/.../HeissRunner.xcodeproj` and the
   generator never writes `DEVELOPMENT_TEAM`, so every install wipes it. The CLI
   is unaffected because it passes the team on the command line — only the GUI
   sees it unset. Fix: have the generator write `DEVELOPMENT_TEAM` from
   `signing.json` (now `96WS9UMR7M`). Flagged 2026-08-04, patched by hand as a
   stopgap, never fixed properly; it recurred 2026-08-19.

### Latent, not currently firing

9. **Posting slots**: 7 enabled at 09:00 including the two parked personas
   (`@arete11plus`, `@sophies11plus`), inert only because the queue is empty. If
   content ever appears, all seven post at the same minute.
10. **Warmup schedules resurrect themselves.** `load()` forward-fills a schedule
    for any account lacking one, so a deleted schedule returns on the next tick.
    Only `enabled: false` sticks.
11. **Denylist rows are inserted once per targetKey forever**, so the 30-day
    window never refreshes — after day 30 a target can be re-engaged repeatedly.
    Inert while engagement mode is off.
12. **Curated post-key mismatch**: `alreadyEngagedKeys` is fed
    `engagementTargets[].targetKey` while `ParsedXPost.key` is
    `x:${matchText}`. The two never match. Inert at 0 rows; would matter once
    the ledger fills.

## Deliberately not done

- **All hosted/SaaS findings** — OAuth origin trust, Lemon webhook, Docker as
  root, rate limits, password auth, unbounded JSON bodies. `apps/web` is not
  deployed.
- **Cloud Drop reclaim double-post** — no content, no queue.
- **Architecture refactors** (`L`): splitting `FarmOrchestrator` (~1,100 lines),
  the CLI god module (~1,900-line `main()`), extracting the Swift dispatch from
  the XCTest target. All correct, all wrong to attempt while the farm has only
  just started working reliably.
- **Store TOCTOU** (`store.ts:260-276`) — real, and it bit us on 2026-08-13 when
  the daemon overwrote a hand edit. The fix touches the hottest path in the
  system and deserves its own change with its own testing.
- **Per-step full-document write** — the orchestrator rewrites all of
  `farm.json` after every device step and scans the activity log twice per step
  for caps. At 4.4 MB this lands directly on step latency. `M` effort, hot path.
- **Device-path test coverage** — `ios-transport`, `runner-install`, `usb.ts`,
  the desktop IPC and the Swift command server have no automated tests. `L`
  effort; needs a fake `devicectl`.
