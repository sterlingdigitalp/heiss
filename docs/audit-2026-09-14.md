# Repository audit — 2026-09-14

Audited commit: `a05a99d`. Scope: core orchestration/storage, farm CLI and controller, USB transport and Swift command handling, web authentication/billing/Cloud Drop, desktop IPC and packaging, dependency manifests, and tests. This is a source and local reproduction audit, not a forensic examination of the Mac or a certification of deployed services.

## Outcome and validation

There are reproducible correctness faults, security exposures in the hosted web path, and avoidable I/O costs. Several August backlog items are still present. The earlier audit's claim that hosted features were not deployed was **not reverified**; web findings below are conditional on deploying those features. No live farm configuration was inspected or changed, and no automation gestures were requested.

- `npm run typecheck`: passed for core, device, farm, and web.
- TypeScript builds: passed for all four packages.
- `npm test`: **193 passed, 0 failed** (154 core, 30 device, 7 farm, 2 web). Repeated successfully after rebuilding workspace packages. The tests include USB discovery against the host and use temporary farm stores; they do not provide end-to-end gesture coverage.
- Desktop packaging and Swift/Xcode compilation were not run. Desktop packaging replaces `dist/Heiss.app`; this audit did not replace the packaged app.
- `npm audit --json`: one affected package, `undici@7.28.0`, with five advisories and an overall high severity. See finding 14 for actual dependency context.
- Isolated reproductions confirmed findings 1–3, 5, 7, 9–11. Other findings are source-derived and say so.
- A limited working-tree credential-pattern scan found only a private-key marker in a test fixture. Reviewed package resolution URLs use the npm registry. No evidence of malicious code or credential exfiltration was identified in the reviewed paths. This does **not** establish that the host, every installed dependency, Git history, or distributed binary is uncompromised.
- Application source was left unchanged. The pre-existing edit to `.handoff-auto.md` was preserved. This report is the only tracked addition.

## Findings, prioritized by impact

### 1. High — controller timeout allows duplicate execution outside the command queue

**Locations:** `apps/farm/src/command-authority.ts:37–65,99,123–161`; `apps/farm/src/cli.ts:577–588`.

The forwarding client returns `{ forwarded: false }` after ten minutes, on a socket error, or after an unreadable response. The CLI interprets this as permission to execute the command locally. The server can still have the original request queued or running; its child timeout is twenty minutes and does not include time spent waiting in the queue. A slow tick followed by a mutating CLI request can therefore execute the same mutation twice and bypass serialization.

**Reproduction:** a temporary socket accepted the request but withheld its reply; an accelerated forwarding timeout returned `{ forwarded: false }` despite successful delivery. The CLI fall-through is directly visible in source.

**Fix:** distinguish “no controller exists” from “outcome unknown after delivery.” Fail closed after delivery and use durable request IDs with status lookup/idempotency. Align client/server timeout semantics; do not retry a possibly executed operation locally.

### 2. High — revision checking does not make store writes atomic

**Locations:** `packages/core/src/store.ts:259–285`; `apps/web/src/server.ts:181–189`.

`save()` reads/checks the revision, then writes a temporary file and renames it without an interprocess lock. Two writers can both read revision N and commit revision N+1, silently discarding one writer's changes. Atomic rename prevents torn JSON, not lost updates. Finding 1 creates one path to concurrent writers; separate processes sharing a store create others.

**Reproduction:** instrumented the filesystem read to deterministically interleave another real `JsonStore.save()` immediately after the first writer read the revision. Both saves returned successfully. The final settings retained `dailyActionCap=111` but lost the other writer's `accountDailyActionCap=12`, reverting it to 25. Instrumentation controlled scheduling; it did not replace either save implementation.

The web server also retains one store instance indefinitely. An external committed revision leaves its later saves conflicting, while requests may already have mutated the in-memory state.

**Fix:** use transactional storage or an interprocess lock covering revision check and commit. Apply web mutations transactionally, with reload/retry on conflicts and rollback on failure.

### 3. High — deleted schedules silently return enabled

**Locations:** `packages/core/src/store.ts:156–185`; `apps/farm/src/cli.ts:2333–2351`; `apps/desktop/renderer.html:62–64`.

Every load creates an enabled warmup schedule for any account without one, and an enabled 09:00 posting slot for any X account without a slot. The CLI/UI explicitly offer removal, but the next load undoes it. A user who removes work can receive unexpected future activity; posting still requires eligible queued content.

**Reproduction:** removed both schedules for a seeded X account, saved, then reopened the store. Both schedules returned.

**Fix:** make legacy migration versioned and one-time, or persist explicit disabled/deleted intent. Add CLI-level remove → reload regression tests for both schedule types.

### 4. High — posting recovery can mark an unconfirmed post as delivered

**Locations:** `ios/HeissRunner/UITests/HeissRunnerUITests.swift:313,356–365`; `packages/core/src/orchestrator.ts:774–788,824–844`.

The host correctly persists `publishAttempted` before sending a publish command. On recovery it asks for `post:verify_published`. The Swift verifier only checks that a matching Post/Share button is absent, and skips normal account verification for this action. It never verifies that the intended content appeared on the intended account.

If delivery failed before the tap and the composer subsequently disappeared, or the app restarted onto another screen, absence of a button can be treated as success. The host then marks the item posted and can report delivery upstream, where media is deleted.

**Evidence:** source inspection; no real posting experiment performed.

**Fix:** require positive evidence for the exact account/content, or preserve an explicit “outcome unknown, needs review” state. A disappeared composer is insufficient proof of publication.

### 5. Medium — the 30-day engagement denylist never refreshes old targets

**Locations:** `packages/core/src/orchestrator.ts:1031–1035,1074–1078`; `packages/core/src/engagement.ts:129–132`.

Successful engagement inserts a target only if its key has never existed. Blocking considers only records from the last thirty days. Once the first record ages out, subsequent successful engagements do not refresh it, so the target remains unblocked immediately after engagement.

**Reproduction:** seeded a 31-day-old record, invoked the actual outcome recorder with a new successful engagement, and queried `activeBlockedTargetKeys`. The just-engaged target was still absent.

**Fix:** record each successful event or upsert the last-success timestamp. Preserve account/action attribution separately from the intended global cooldown.

### 6. High if hosted — unauthenticated requests can consume unbounded memory and block the web event loop

**Locations:** `apps/web/src/server.ts:65–72,426–452,503–509`; `packages/core/src/auth.ts:7–10,25`.

JSON bodies are buffered without a size limit, including public signup/login/magic-link routes. There is no application rate limiting. Password hashing and verification use synchronous scrypt on the main thread. Repeated signup/login requests can block all other requests; oversized request bodies can exhaust memory. Magic requests also create users and farm rows before checking whether email delivery is configured, permitting persistent growth even when that feature returns 503.

**Evidence:** source inspection. No load or denial-of-service traffic was generated.

**Fix:** cap body bytes as they arrive, validate schemas and input lengths, rate-limit by source and account, bound hash concurrency using asynchronous hashing, and validate provider configuration before creating state. Retain proxy limits as an additional layer.

### 7. High, configuration-dependent — development magic tokens remain available in production

**Locations:** `apps/web/src/server.ts:177–180,447–488`.

Production startup checks the session secret but does not reject `HEISS_DEV_MAGIC_LINKS=1`. With that flag, an unauthenticated magic-link request returns the login token for the supplied email directly in JSON, including existing users. Anyone can complete login without access to the mailbox.

**Reproduction:** started a temporary server with `NODE_ENV=production`, a 32-character secret, and the dev flag. `/api/magic/request` returned a token for an existing test user.

**Fix:** reject this configuration on production startup and never return development tokens in production responses. No evidence was gathered that a deployed service currently has this flag enabled.

### 8. Medium if Google login is enabled — OAuth state is not tied to the initiating browser

**Locations:** `apps/web/src/server.ts:123–141,234–248`.

State contains a signed timestamp and nonce, but no browser session/cookie binding and no consumed-nonce registry. A valid state/code flow initiated in one browser can be completed in another. An attacker can initiate authorization for their own account and induce a victim to finish that callback, logging the victim into the attacker's account and potentially placing the victim's uploads there.

**Evidence:** source inspection; no Google account login performed. This is login CSRF, not a claim that the state signature itself can be forged.

**Fix:** bind the authorization transaction to a secure browser cookie/session, consume state once, and use PKCE as appropriate.

### 9. High if Cloud Drop is used — stale claims can repeat already completed deliveries

**Locations:** `apps/web/src/server.ts:355–387`; `apps/farm/src/cli.ts:252–282`.

Claims expire after ten minutes with no lease renewal or fencing token. Reclaims return every target, including those already present in `postedAccountIds`. A new local runner imports the item with an empty `postedAccountIds` array. It can schedule accounts that already posted, while the old runner may still be processing its locally persisted copy. Scheduling content for later also outlasts the fixed ten-minute claim window.

**Reproduction:** claimed a two-account text drop, completed account A, advanced the test clock eleven minutes, then claimed from another runner. The response transferred the claim and still included A in its target list. The fresh local import's empty completion list is source-confirmed. No duplicate public post was attempted.

**Fix:** track delivery and leases per account, omit completed targets, import completion state, renew ownership, and require a fencing token on completion. Treat uncertain publication separately from safe retry.

### 10. Medium if hosted — repeated runner syncs bypass plan limits and preserve removed inventory

**Locations:** `apps/web/src/server.ts:290–333`.

Capacity enforcement validates only the current payload length. Sync then upserts records and never removes previously synced real accounts/devices that were omitted. Sending individually valid batches accumulates inventory beyond the plan, and accounts removed on the Mac remain in the dashboard.

**Reproduction:** a free user sent two sync requests, each containing one different device. Both returned 200; overview then returned two devices despite a one-device plan.

**Fix:** define authoritative snapshot or runner-scoped reconciliation semantics, validate resulting inventory totals, and deliberately reconcile removed accounts, slots, and outstanding deliveries.

### 11. Medium if Cloud Drop is used — cancelling/completing one item destroys another item's shared media

**Locations:** `apps/web/src/server.ts:414–420,669–696,723–728`.

Multiple drops may reference the same authenticated upload. Completion/cancellation unconditionally deletes that upload without checking other content references. The surviving queue item remains claimable but cannot download its media.

**Reproduction:** uploaded a small temporary file, created two drops referencing it, cancelled the first, and claimed the second. Download returned 404.

**Fix:** introduce asset ownership/reference counting or immutable per-drop copies. Garbage-collect files only when no pending delivery references them. Define cleanup for abandoned uploads too; the current API has no general upload-delete operation.

### 12. Medium if billing is used — signed webhook events can regress subscription state

**Locations:** `apps/web/src/server.ts:560–589`.

Signature validation is present. The handler nevertheless accepts any non-cancellation event carrying a recognized variant as grounds to grant a paid plan. It does not validate entitlement status, event ordering, or whether the event belongs to the user's current subscription. An old signed event delivered after an expiry can restore paid access; a cancellation for an old subscription can revoke a newer one. This requires a valid provider event, not a forged signature.

**Evidence:** source inspection.

**Fix:** process explicit entitlement events, track subscription IDs and provider timestamps/event IDs, reject stale transitions, and reconcile ambiguous events against provider state. Define how access behaves through paid-through cancellation dates.

### 13. Medium — avoidable full-file I/O compounds device and web latency

**Locations:** `packages/device/src/ios-transport.ts:264–286`; `packages/core/src/orchestrator.ts:791–798,844,1231`; `packages/core/src/store.ts:259–280`; `apps/web/src/server.ts:395–401`; `apps/farm/src/cli.ts:261–271`; `apps/desktop/main.cjs:91–93`.

- Each individual posting action carries the same media references, and transport copies them to the phone again under a fresh command ID. Caption, publish, and recovery steps need not each restage a large video. Stage once per content/session and reuse a stable validated reference.
- Individual action checkpoints synchronously read/parse and serialize/write the whole farm state. Action-cap evaluation repeatedly scans activity and converts dates. Batched warmups already avoid a save per gesture; the cost remains in individual posting/candidate steps and broader store operations. Use incremental transactions and per-day counters/indexes.
- Web downloads use `readFileSync` for files allowed to be as large as the default 2 GiB upload cap. Cloud downloads use `arrayBuffer()` and synchronous writes. Concurrent transfers can consume multiples of a file's size in RAM. Stream both directions with bounds/backpressure.
- Desktop log display reads the entire controller log before taking its final 12,000 characters. Read only a tail range and rotate logs.

**Evidence:** source inspection; no production latency benchmark or large-file load test was run. These are specific avoidable costs, not measured slowdown claims.

### 14. Medium remediation priority — locked dependency has known vulnerabilities

**Location:** `package-lock.json:1014`; dependency chain: `@heiss/desktop → electron@43.1.0 → @electron/get@5.0.0 → undici@7.28.0`.

The npm advisory scan reports five advisories against this version, including a high-severity shared-cache disclosure/parser issue. The [upstream advisory](https://github.com/nodejs/undici/security/advisories/GHSA-4cwx-7wf7-3272) identifies 7.29.0 as the patched 7.x version and requires use of the cache interceptor for that particular issue.

Reviewed `@electron/get` code loads Undici for proxy setup; no use of the affected shared-cache interceptor was identified there. This is a dependency hygiene finding with **unproven application exploitability**, not evidence that dashboard data leaked. Node's built-in `fetch` is a separate runtime dependency and is not assessed by this npm lockfile result.

**Fix:** update the locked transitive dependency within a supported range, rebuild/check Electron downloads and packaging, and rerun the advisory scan. Do not blindly apply a forced major-version upgrade.

## Additional improvement backlog

- **Curated post deduplication is disconnected:** `apps/farm/src/cli.ts:375–389` compares `engagementTargets.targetKey` to `ParsedXPost.key` (`x:` plus match text in `packages/core/src/x-posts.ts`). The successful curated path also does not persist the chosen post key. Separate account/handle cooldowns from actual post IDs and record them consistently. Existing daily/target limits still operate, so this is not an assertion that every run repeats an engagement.
- **Runner build-lock reclaim is still check-then-delete:** `packages/device/src/runner-lock.ts:116–123`. Re-reading does not atomically couple ownership validation and unlink; simultaneous stale-lock reclaimers can remove a replacement lock. A newly created file can also be read before its JSON is fully written and classified as corrupt/stale. Add multi-process contention tests and use an OS lock or carefully designed atomic lock-directory protocol. This was not reproduced in this audit.
- **Desktop boundary hardening:** `apps/desktop/main.cjs:103–134` exposes unrestricted farm arguments and external URL schemes to the renderer, without sender validation/navigation restrictions. No renderer compromise was demonstrated. Add typed IPC argument validation, a URL scheme allowlist, sender checks, navigation policy, and a CSP. `runFarm` also lacks a child `error` listener, so missing `npx`/spawn failure can become an unhandled main-process error.
- **Deployment footprint:** `Dockerfile` copies the full development dependency tree, including desktop tooling, into a root-run runtime image. Prune to the web dependency closure and run under a dedicated user with writable data-volume ownership. Desktop packaging uses an ad-hoc signature and no notarization; it is not a complete external Mac distribution pipeline.
- **Checks miss shipped surfaces:** desktop typecheck is a no-op and excluded from root typecheck; no automated Swift/transport/desktop IPC integration checks were found. The web suite contains just two tests. Add targeted regressions for the cases above and a fake `devicectl` contract harness. Make tests build prerequisite workspace exports: `@heiss/core`/`@heiss/device` resolve to ignored `dist`, whereas README's fresh-install sequence runs tests before building.
- **Documentation and module boundaries:** README still advertises retired autonomous engagement and different defaults from the current CLI. Update it against executable command behavior. After correctness fixes, extract web routes/services, CLI command handlers, and Swift action dispatch from their large modules; avoid a broad refactor before preserving behavior with focused tests.

## Suggested repair order

1. Fix controller fail-open behavior and store atomicity together; add contention/unknown-outcome tests.
2. Make schedule removal durable and publication recovery conservative.
3. Repair engagement timestamps and consistent post identity tracking.
4. Before exposing hosted features, fix production dev-token rejection, request limits/auth throttling, OAuth binding, and delivery leases.
5. Repair Cloud Drop asset lifecycle, sync reconciliation, and billing event ordering.
6. Update the vulnerable dependency and address repeated media copies/large synchronous I/O.

Keep each behavior change independently reviewable. The existing green suite does not cover the reproduced failures.
